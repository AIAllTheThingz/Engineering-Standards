## Summary

Version `1.2.0` is the selected next semantic version for the backward-compatible governance, workflow, validation, standards, examples, release-lifecycle, and controlled Codex behavior work accumulated after published `v1.1.0`.

This file is a release-preparation record. It does not authorize a tag, claim publication, or declare a pre-freeze preparation SHA to be the final candidate. PR #100 merged the primary release-preparation change set as `0a47444c0416c397dad769e7e66f9ad7e3119195`. The exact candidate will be the unchanged protected `master` SHA selected only after remaining release-preparation status synchronization is merged and the tree is frozen. Candidate identity is then recorded in release lifecycle evidence rather than by a post-selection metadata commit that would move the candidate again.

The published `v1.1.0` record remains historical and unchanged.

## Release Scope

### Governance And Release Controls

- Version-aware governance contract `1.2.0` support with structured ownership, standards consumption, workflow-interface, evidence-path, and exception records.
- Aggregate validation registry and authoritative complete maintainer validation profile.

### Language Standards And Workflows

- First-class Python and Bash central standards and cross-standard handoffs.

- Hash-locked Python functional validation, package inspection, dependency audit, isolated installation, smoke testing, SBOM, and evidence.
- Hash-verified Bash functional validation with bounded read-only execution and maintained example coverage.
- Maintained functional examples and isolated home-lab demonstrations with explicit non-production boundaries.

### Codex Skill Governance

- Governed `enterprise-powershell` skill delivery and deterministic skill validation.
- Controlled probabilistic behavior evaluator with approved model/sampling contract.
- Trusted default-branch and isolated Actions evaluation paths.
- Structured Outputs-safe observation schema and schema `1.3.0` evidence provenance.

- Provider/preflight hardening and bounded failure diagnostics.
- Human-adjudicated routing/safety taxonomy and ten-case behavior corpus.
- Disambiguated `NotSelected`, `Uncertain`, and explicit `Selected + Proceed` fixtures without lowering safety thresholds or introducing permissive alternate outcomes.

## Compatibility

No breaking downstream change is intended.

- Published `v1.1.0` remains supported until `v1.2.0` is actually published.
- Central governance workflow interface remains `1.0.0`.
- Project-manifest schemas `1.0.0`, `1.1.0`, and `1.2.0` remain accepted in the prepared contract.
- Test-evidence schemas remain `1.0.0` and `1.1.0`.
- Completion-result schemas remain `1.0.0` and `1.1.0`.
- Historical documents and release evidence are not rewritten to the new semantic version.

The prepared compatibility contract is `Preview`, not a production compatibility promise.

## Consumer Guidance

Until publication:

- Production consumers should continue using immutable published `v1.1.0` or another explicitly documented immutable authority.
- Do not pin production governance to `master` or assume prepared `1.2.0` is published.
- Consumers requiring the already verified repaired central reusable workflow may continue using the immutable canary-validated authority recorded in [Downstream Compatibility](../DOWNSTREAM_COMPATIBILITY.md).
- No immediate migration is required merely because `1.2.0` is being prepared.

After publication, release notes and the compatibility matrix will state whether consumers should adopt at normal cadence and which exact immutable references are supported.

## Exact-Candidate Release Gates Still Required

After all release-preparation status synchronization is merged, maintainers must select one unchanged candidate SHA and perform the existing release process against that exact candidate:

1. Complete Governance CI success validation.
2. Complete the controlled-failure proof and verify its artifact.
3. Run all five downstream governance canary scenarios.
4. Independently download and verify required artifacts and hashes.
5. Verify branch/tag protection observations required by the lifecycle record.
6. Complete the PreRelease lifecycle record against the same candidate SHA.
7. Complete attributable human behavior adjudication and formal release approvals.
8. Obtain explicit `v1.2.0` tag and GitHub Release publication authorization.
9. Create the annotated protected tag and publish only after authorization.
10. Re-fetch external state and pass Publication and PostRelease validation.

Any commit that changes the final candidate invalidates exact-target evidence and must be handled under the existing release lifecycle rules. Metadata-only commits that occur before candidate freeze are preparation history, not exact-candidate evidence.

## Versioning Rationale

`1.2.0` is a minor release because the accumulated work adds backward-compatible governance capabilities, new standards, validation categories, workflows, schemas, examples, and advisory/controlled evaluation infrastructure without intentionally removing a supported contract or imposing a breaking workflow-interface change.

This follows [Versioning](../VERSIONING.md): use a minor increment for backward-compatible governance additions and reserve major increments for downstream-breaking obligations.

## KISS, YAGNI, And DRY

Release preparation reuses the repository's existing lifecycle validator, downstream compatibility contract, release status, consolidation record, and changelog. It does not introduce another release framework, duplicate release ledger, or speculative publication mechanism.
